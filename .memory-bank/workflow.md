# Рабочий процесс

## Начало

1. Прочитать `CLAUDE.md`, `AGENTS.md` и все файлы памяти.
2. Проверить `git status --short --branch`, относящийся к задаче код и документацию.
3. По-русски сформулировать результат и критерий готовности, задать необходимые вопросы.
4. Если есть более эффективный путь, сообщить о нём и обосновать выбор.
5. Разделить независимую работу между агентами с явными границами файлов; общую проверку выполнить после объединения результатов.
6. Для содержательной задачи заполнить короткую карточку из [task-template.md](task-template.md) в журнале работ. Выбрать проверки по [verification-matrix.md](verification-matrix.md).

## Выполнение и проверка

Делать изменения в пределах задачи. Регулярно сообщать о фактах, решениях и ограничениях.
Запустить существующие проверки из `testing.md` до коммита. Для новой функциональности добавить тесты, для исправления ошибки проверить воспроизведение ошибки тестом, когда это возможно.
Не заменять тесты Android проверкой Markdown. Указывать каждый незапущенный или заблокированный этап отдельно.
После изменения памяти запускать `scripts/project/Check-Memory.ps1`; перед Android-сборкой диагностировать окружение через `scripts/project/Test-Environment.ps1`.

## Завершение

Обновить `work-log.md`, `CHANGELOG.md` и затронутые тематические документы. Решения записать в `decisions.md`, обнаруженные ловушки в `common-mistakes.md`.
Новый документ памяти зарегистрировать в двух картах. Применить правило уведомления из `user-updates.md`.
После успешных обязательных проверок выполнить запрошенный коммит в формате Conventional Commits, затем push в репозиторий владельца и выпуск по `deployment.md`.
При блокировке зафиксировать точную причину и необходимый следующий шаг, не объявляя весь цикл завершённым.
Перед выпуском заполнить [release-checklist.md](release-checklist.md); пустое доказательство не считать пройденной проверкой.
Итог: результат, проверки, ограничения, минимум пять советов с пользой и рисками, затем таблица сессии из `CLAUDE.md`.
