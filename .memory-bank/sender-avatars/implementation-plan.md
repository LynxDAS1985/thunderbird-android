# План реализации аватаров отправителей

## 1. Цель

Собрать все настройки изображений отправителя в одном месте и обеспечить одинаковый результат в списке писем, открытом письме и Android-уведомлении.

Итоговый путь пользователя:

`Настройки → Основные → Аватары отправителей`.

Визуальные требования и схема механизма зафиксированы в [mockups.md](mockups.md). При расхождении текста плана и декоративной детали изображения приоритет имеет текст плана; при расхождении состава или логики настроек требуется отдельное решение владельца.

## 1.1. Обязательные улучшения

Эти требования входят в работу и не считаются необязательными идеями:

1. Один `SenderAvatarResolver` выбирает аватар для списка, открытого письма, участников и уведомлений.
2. Зелёный щит запрещён без проверки подлинности конкретного письма. Наличие контакта, картинки или закэшированного логотипа не является подтверждением.
3. Единый экран содержит полный выбор источников, явный приоритет, fallback и объяснение зависимостей.
4. Обновление поверх старой установки проверяется автоматически и вручную для всех комбинаций трёх прежних параметров.
5. Сетевые логотипы и новый resolver защищены отдельным feature flag для пробного выпуска; выключенное состояние полностью сохраняет старое поведение.
6. Настройка аватара в уведомлениях входит в резервную копию и восстанавливается при импорте вместе с остальными настройками аватаров.

### 1.2. Проверка новых обязательных пунктов от 2026-10-10

| Требование | Проверка отсутствия | Почему уместно | Этап |
|---|---|---|---|
| Вынести выбор аватара в единый `SenderAvatarResolver` | Поиск `SenderAvatarResolver` по `core`, `feature`, `legacy` не нашёл реализации | Сейчас список, открытое письмо и уведомления выбирают изображение разными цепочками | 3–6 |
| Запретить щит без результата проверки письма | `SenderVerification` и контракт привязки проверки к письму отсутствуют | Фото контакта, логотип или зелёный цвет не доказывают подлинность отправителя | 3 и 8 |
| Проверить обновление поверх старого APK | Автоматический тест 8 комбинаций есть, сценарии `MIGRATE-01`–`MIGRATE-07` на телефоне не пройдены | Только реальное обновление проверит Android-хранилище и сохранённые аккаунты | 1 и 9 |
| Добавить настройку уведомлений в резервную копию | `showContactPictureInNotification` отсутствует в `GeneralSettingsDescriptions.SETTINGS` | Иначе после переноса или восстановления телефона этот выбор потеряется | 1 и 9 |

Итоговый порядок выбора изображения:

1. Проверить, разрешены ли аватары в выбранном месте интерфейса.
2. Попробовать первый включённый источник согласно выбранному приоритету.
3. Если результат отсутствует или недопустим, попробовать второй источник.
4. Если изображения нет, показать выбранную заглушку.
5. Показывать знак подтверждения только для логотипа, проверенного для конкретного письма.

## 2. Осмотр текущей реализации

### Настройки

- `legacy/ui/legacy/src/main/res/xml/general_settings.xml` содержит экраны `Вид` и `Уведомления`.
- Там находятся ключи `messagelist_show_contact_picture`, `messagelist_colorize_missing_contact_pictures` и `notification_show_contact_picture`.
- `legacy/ui/legacy/src/main/java/com/fsck/k9/ui/settings/general/GeneralSettingsFragment.kt` подключает XML.
- `legacy/ui/legacy/src/main/java/com/fsck/k9/ui/settings/general/GeneralSettingsDataStore.kt` читает и записывает значения через менеджеры проекта.
- `DisplayMessageListSettings` и `NotificationPreference` являются моделями текущих настроек.
- `DefaultMessageListPreferencesManager` и `DefaultNotificationPreferenceManager` сохраняют значения.

Сейчас работает так: список и уведомления управляются разными переключателями, выбора источника и приоритета нет.

### Список писем

- Legacy: `MessageListAdapter` → `MessageViewHolder.setContactPicture()` → `ContactPictureLoader` → `ContactImageBitmapDecoder`.
- Compose-элемент legacy-списка: `ComposableMessageViewHolder` → `MessageItemContent()` → `ContactRepository.getPhotoUri()`.
- Новый Compose-список: `MessageListFragment.loadMessages()` → `ContactRepository.getPhotoUri()` → `toMessageItemUi()`.
- Отрисовка Compose: `Avatar.Image`/`Avatar.Monogram` → `MessageItemAvatar` или `MessageItemAvatarCircle` → `RemoteImage`.

Сейчас работает так: фотография берётся из контактов Android; при отсутствии показывается монограмма.

### Уведомления

- `SingleMessageNotificationCreator.setAvatar()` проверяет настройку и вызывает `NotificationResourceProvider.avatar()`.
- `K9NotificationResourceProvider.avatar()` создаёт bitmap через текущий загрузчик изображения контакта.
- Текущий контракт получает только `Address`; этого недостаточно для проверки BIMI конкретного письма.

Сейчас работает так: уведомление получает локально созданное изображение/заглушку и не знает результата проверки отправителя.

### Открытое письмо

- `legacy/ui/legacy/src/main/java/com/fsck/k9/ui/messageview/MessageTopView.kt` уже использует `ContactRepository`.
- Перед реализацией нужно полностью проследить модель заголовка письма и существующий компонент аватара; этот путь пока не считать реализованным.
- Отдельно проверить экран подробностей участников: `MessageDetailsViewModel`, `MessageDetailsFragment` и `ParticipantItem`. Он использует контактные данные и легко останется на старой логике.

## 3. Сравнение вариантов

| Вариант | Что делаем | Цена | Риск | Решение |
|---|---|---:|---:|---|
| Быстрый | Добавляем загрузку логотипа отдельно в каждый экран | Меньше кода сначала | Разные правила, повторные запросы, разные аватары | Не выбран |
| Общий resolver | Один сервис выбирает источник, проверяет настройки и возвращает единый результат | Больше подготовительной работы | Нужно аккуратно провести зависимости | Выбран |

Выбран общий resolver, потому что функция используется минимум в трёх независимых путях отображения и должна одинаково обрабатывать ошибки, приоритет и подтверждение.

## 4. Целевая модель

Предлагаемые сущности; точные пакеты подтверждаются на этапе проверки зависимостей:

```kotlin
sealed interface SenderAvatar {
    data class Image(
        val uri: String,
        val source: Source,
        val isVerified: Boolean,
    ) : SenderAvatar

    data class Monogram(val value: String, val colorKey: String) : SenderAvatar
    data object GenericIcon : SenderAvatar
}

enum class Source { CONTACT, COMPANY_LOGO }
enum class SourcePriority { CONTACT_FIRST, COMPANY_FIRST }
enum class FallbackStyle { COLORED_MONOGRAM, GENERIC_ICON }
enum class Placement { MESSAGE_LIST, MESSAGE_VIEW, NOTIFICATION }
```

Вход `SenderAvatarResolver`:

- адрес отправителя;
- стабильный идентификатор сообщения;
- место показа;
- отображаемое имя;
- доверенный результат почтовой аутентификации, если он доступен;
- текущие настройки;
- политика сети.

Выход:

- готовый `SenderAvatar`;
- причина fallback для журнала отладки без адреса и содержимого письма;
- срок действия сетевого результата.

## 5. Полный алгоритм

1. Если главный переключатель выключен — вернуть `null`.
2. Если отключено текущее место показа — вернуть `null`.
3. Составить порядок включённых источников по `SourcePriority`.
4. Для контакта запросить точное совпадение полного email-адреса. Не сопоставлять только по имени.
5. Для логотипа определить организационный домен отправителя и проверить разрешение сетевой загрузки.
6. Сначала проверить положительный и отрицательный кэш.
7. Получить BIMI DNS-запись и допустимый HTTPS-адрес логотипа.
8. Ограничить редиректы, размер ответа, время ожидания и тип содержимого; запретить локальные и служебные IP-адреса.
9. Безопасно проверить SVG без скриптов, внешних ресурсов и XML entities.
10. Отдельно установить `isVerified=true` только при доверенном результате DMARC alignment и допустимом BIMI/VMC/CMC-подтверждении конкретного письма.
11. Если источник не дал допустимого результата, перейти к следующему.
12. Если источники закончились, вернуть выбранную монограмму или стандартную иконку.
13. UI показывает щит только при `source=COMPANY_LOGO && isVerified=true`.

## 6. Настройки и отсутствие конфликтов

Новый экран добавить корневым `PreferenceScreen` в `general_settings.xml` рядом с `Вид` и `Уведомления`.

### Состав экрана

| Раздел | Настройка | Поведение зависимости |
|---|---|---|
| Общая | Показывать аватары | Выключает и визуально блокирует все дочерние настройки |
| Источники | Фото из контактов | Работает локально, требует разрешение Android Contacts |
| Источники | Проверенные логотипы компаний | Разрешает DNS/HTTPS-загрузку |
| Приоритет | Фото из контактов / Логотип компании | Доступно только когда включены оба источника |
| Заглушка | Цветной круг / Стандартная иконка | Используется после неудачи всех источников |
| Размещение | В списке писем | Независимый переключатель |
| Размещение | В уведомлениях | Независимый переключатель |
| Размещение | В открытом письме | Независимый переключатель |
| Безопасность | Значок подтверждения | Доступен только для включённых логотипов; не меняет саму проверку |
| Сеть | Только по Wi-Fi | При мобильной сети resolver пропускает сетевой источник |
| Обслуживание | Очистить кэш логотипов | Удаляет только логотипы и результаты их загрузки |
| Проверка | Предпросмотр | Показывает результат текущей комбинации без сохранения личных данных |

### Перенос старых значений

- `messagelist_show_contact_picture` становится исходным значением главного переключателя и `В списке писем`.
- `messagelist_colorize_missing_contact_pictures` определяет первоначальную заглушку.
- `notification_show_contact_picture` становится значением `В уведомлениях`.
- `Фото из контактов` при обновлении включено, чтобы сохранить текущее поведение.
- Сетевой источник при первом обновлении лучше оставить выключенным до принятия текста о приватности и способа доверенной проверки.
- Старые ключи не удалять в первой версии миграции. Сначала прочитать их, записать новые и проверить откат на старую версию.
- В старых разделах удалить переключатели только после появления нового экрана; не оставлять два элемента для одного значения.

## 9. Опасные зоны

- Приватность: сетевой запрос раскрывает домен корреспондента и время обращения.
- Безопасность: неправильный щит создаёт ложное доверие к фишинговому письму.
- Производительность: DNS/HTTP в строке списка замедлит прокрутку.
- Совместимость: удаление старых ключей может сломать обновление и откат.
- Уведомления: ожидание сети задержит важное уведомление.
- SVG: недоверенный файл нельзя открывать через WebView или парсер с внешними ресурсами.

## 10. Откат

Каждый этап должен быть отдельным логическим commit. При проблеме:

1. Выключить сетевой источник feature flag или настройкой по умолчанию.
2. Сохранить чтение старых preference-ключей.
3. Вернуть UI к контакту/монограмме без удаления пользовательских значений.
4. Не очищать общий кэш приложения; удалять только namespace логотипов.
5. Для отката релиза установить предыдущий подписанный APK совместимым способом; проверить, что старые настройки читаются.
